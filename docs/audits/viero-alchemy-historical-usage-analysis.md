# Viero Alchemy historical usage analysis

**Audit date:** 2026-10-15 (Asia/Jakarta)
**Scope:** Alchemy account usage queried with the official `@alchemy/cli` and a read-only repository/VPS architecture comparison.
**Production safety:** Viero services were not started, changed, or restarted. No blockchain transaction was sent.

## Evidence labels

- **CONFIRMED** — returned by Alchemy or directly observed in source/service state.
- **ALLOCATED ESTIMATE** — arithmetic allocation of the account total, not an invoice line item.
- **CODE-INFERRED** — follows from repository control flow, not provider attribution.
- **UNKNOWN** — not exposed by this CLI query or not safely attributable to Viero.

## Operational-context correction (2026-10-15)

The original comparison treated October 10 as the end of all Viero-related RPC activity. That assumption was incomplete. On October 10, autonomous Viero operations were stopped, but a separate/manual liquidity-provision bot continued using the same Alchemy RPC infrastructure on Robinhood Chain (4663) and BNB Smart Chain (56).

Therefore, Oct 11–14 usage must be interpreted as **manual LP activity plus any shared/account-level activity**, not as an expected zero baseline. The measured post-stop decrease still supports the conclusion that autonomous workloads were a major incremental consumer, but it cannot be used to estimate autonomous usage by simple subtraction. See [viero-rpc-workload-attribution.md](viero-rpc-workload-attribution.md) for the separated workload analysis.

## Comparison with Viero architecture

The repository audit at [viero-rpc-cost-investigation.md](viero-rpc-cost-investigation.md) identified the following code-inferred consumers:

- Routine token-first screening is GMGN-only and does not call EVM RPC.
- Candidate verification/enrichment uses pool identity recovery, block-pinned reads, historical logs, depth/tick reads, and transaction/block lookups.
- Open-position management runs on a five-minute cadence and performs fresh verification, fee reads, pricing, and entry-basis reconciliation.
- Startup preflight performs chain/block/code checks.
- The legacy indexer can perform large historical log scans, but it was disabled in the inspected production state.
- Telegram long-poll/reporting is not itself EVM RPC; refresh/screen actions are exceptions.

The measured pre-stop method mix (`eth_call`, `eth_getLogs`, block lookups, and code checks) is **consistent with** candidate enrichment, position management, and preflight. That is evidence-compatible attribution, not proof that the Alchemy app was used exclusively by Viero.

The retained post-stop residual is now **consistent with the reported continuation of manual LP operations**. It is not evidence that autonomous Viero remained active. The large post-stop `alchemy_getAssetTransfers` component still requires source correlation because this repository's normal Viero paths do not call that method directly; it may belong to the manual bot or another SDK/client.

## Actual versus estimated cost

- **Actual/provider-reported:** $4.41 month-to-date for 9,795,410 CU, as returned by `usage summary`.
- **Allocated estimates:** the daily and period USD figures above distribute that $4.41 linearly by CU. Alchemy plan pricing, tiering, credits, and any non-linear billing treatment were not returned by the timeseries command, so daily USD figures must not be treated as invoice values.
- **Not established:** the historical reported `$2–$2.50/day` Viero-only cost. The retained Oct 9 account total alone is estimated at $1.7949, but attribution and billing allocation remain unverified.

## Confirmed observations versus hypotheses

**Confirmed:**

1. Official CLI v0.25.0 authenticated successfully.
2. The account had 9,795,410 CU and $4.41 month-to-date at the query time.
3. The CLI returned daily/grouped data only from Oct 8 through Oct 14.
4. Average account consumption decreased 83.42% between the retained pre-stop subset and Oct 11–14.
5. BNB was the dominant returned network, and `eth_call`/`eth_getLogs` were the largest standard EVM methods.
6. Viero services had been inspected as inactive/stopped in the prior audit; this audit did not start them.

**Hypotheses requiring correlation:**

1. Most of the Oct 8–9 `eth_call`/`eth_getLogs`/block activity was the combined autonomous-plus-manual workload, with autonomous candidate enrichment and position management likely the dominant incremental component.
2. The residual Oct 11–14 activity is plausibly manual LP activity, but exact operation-level correlation was not available locally.
3. The prior $2–$2.50/day estimate may represent combined account-level/manual-plus-autonomous billing, not Viero-only autonomous cost.

## Remaining unknowns

- Oct 1–7 daily history was unavailable through this CLI query.
- The CLI did not provide request-level process ownership, endpoint URL, retry count, latency, or a Viero release identifier.
- The opaque app ID was not mapped to a Viero deployment in the returned data.
- No direct Viero request counter exists in the repository, so method-level attribution is not measurable.
- Daily provider billing cannot be reconstructed exactly from compute units without plan/rate/credit details.
- The exact manual-operation source and timestamps for post-stop `alchemy_getAssetTransfers` activity remain unresolved.

## Recommended next investigation

1. In the Alchemy Dashboard, export the usage/billing report for Oct 1–15, including app, network, method, and (if available) endpoint/request-type dimensions; verify whether Oct 1–7 is retained there.
2. Map the opaque app ID to the Viero Alchemy app in the dashboard without placing the ID or any credential in source or reports.
3. Add a local, read-only PublicClient transport counter keyed by release, process role, chain, method, retry, and operation class. Never log URLs, headers, or payload secrets.
4. Compare those counters with the dashboard export over identical UTC windows, keeping the indexer disabled and services stopped for the baseline.
5. Investigate the manual bot/SDK owner of `alchemy_getAssetTransfers` separately; do not attribute the post-stop residual to autonomous Viero without that correlation.

No runtime code, production configuration, service state, strategy, or blockchain state was modified by this audit.
